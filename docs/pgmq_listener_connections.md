# Постоянная подписка на PGMQ listener

## Назначение документа

Документ описывает, как в проекте устроено ожидание событий `LISTEN/NOTIFY` для очередей `PGMQ`, почему для него
используются отдельные соединения PostgreSQL и какие ограничения это решение вводит.

## Что в этом контексте означает постоянная подписка

Под постоянной подпиской здесь понимается долго живущий `LISTEN` на канал вида `pgmq.q_<queue_name>.INSERT`, который
сохраняется между вызовами `wait_for_notification(...)`.

Практически это означает следующее:

- для каждой очереди создается отдельный `asyncpg.Connection`;
- listener регистрируется на этом соединении один раз;
- следующие вызовы `wait_for_notification(...)` переиспользуют уже созданное соединение, пока оно не закрыто.

Такое поведение реализовано в `src/multichannel_gateway/infrastructure/pg_message_queue.py`. Оно заменяет прежнюю схему,
где listener жил только внутри одного `pool.acquire()` и снимался сразу после завершения ожидания.

---

## Почему не использовать единый пул с двумя соединениями, которые никогда не возвращаются в пул?

Если взять соединение из пула и не возвращать, получится следующее:

- Резервируются два физических соединения под LISTEN/NOTIFY.
- Для каждой очереди нужно свое долго живущее соединение, значит эти соединения будут постоянно заняты.
- Они перестают участвовать в нормальном acquire/release, то есть уменьшают полезную емкость пула для обычных
  send/read/delete.

Почему единый пул это плохая идея:

- Пул нужен для коротких операций с временным владением connection.
- LISTEN/NOTIFY нужен на долгоживущем соединении с отдельным жизненным циклом.

Смешивать эти два режима в одном пуле неудобно: пул начинает содержать "мертвую" для остальных запросов емкость.

Есть и практический момент: у `asyncpg` корректный путь работы с пулом предполагает, что взятое через `pool.acquire()`
соединение будет возвращено. Если держать его бесконечно, то:

- можно словить starvation при маленьком max_size;
- сложнее управлять закрытием/переподключением;
- семантически это уже не пул, а просто вручную удерживаемые отдельные соединения.

## Как теперь устроено ожидание уведомлений

Метод `wait_for_notification(queue_name, timeout)` работает так:

1. Формирует имя канала `pgmq.q_<queue_name>.INSERT`.
2. Проверяет, есть ли уже listener connection в `_listener_conns[queue_name]`.
3. Если соединения нет или оно закрыто, создает новое connection через `ConnManager.get_connection(...)`.
4. Регистрирует callback через `conn.add_listener(...)`.
5. Сохраняет connection и callback в словари экземпляра.
6. Ждет срабатывания общего `asyncio.Event`.

Создание listener происходит лениво: только при первом вызове ожидания для конкретной очереди. При этом остальные
операции `PGMessageQueue`, такие как `send`, `read`, `delete`, `archive` и `set_vt`, по-прежнему используют `asyncpg`
pool.

---

## Как в этой схеме используется `asyncio.Event`

Экземпляр `PGMessageQueue` хранит один общий `self._event = asyncio.Event()`. Метод `wait_for_notification(...)` ждет
его через `await asyncio.wait_for(self._event.wait(), timeout)`.

`self._event.set()` используется в трех случаях:

- callback, зарегистрированный через `add_listener(...)`, вызывает `self._event.set()`, когда PostgreSQL присылает
  уведомление по нужному каналу;
- сразу после первой регистрации listener вызывается `self._event.set()`, чтобы worker немедленно сделал повторный
  `read()` и не пропустил сообщение, которое могло попасть в очередь между предыдущим чтением и `add_listener(...)`;
- при `close()` вызывается `self._event.set()`, чтобы разбудить текущее ожидание и дать worker выйти из
  `wait_for_notification(...)`.

После успешного пробуждения `wait_for_notification(...)` вызывает `self._event.clear()`. То есть `Event` служит только
триггером: "перестань ждать и еще раз проверь очередь".

Важно, что `Event` общий для всего экземпляра `PGMessageQueue`, а не отдельный на каждую очередь. Поэтому уведомление
по одной очереди будит оба воркера: и тот, который слушает `to_cw`, и тот, который слушает `from_cw`. После
пробуждения каждый воркер делает свой `read()` уже по своей очереди. В итоге сообщение получает только нужный воркер,
а второй либо получает пустой результат чтения, либо может подобрать сообщение, которое уже лежало в его очереди.

Это поведение не только побочный эффект общего `Event`, но и полезное свойство текущей схемы. Если отдельное
уведомление было пропущено, listener временно не был зарегистрирован или соединение пережило сбой, сообщение может уже
лежать в очереди без нового `NOTIFY`. В такой ситуации пробуждение от активности в другой очереди дает второму воркеру
шанс раньше сделать повторный `read()` и обработать накопившееся сообщение, не дожидаясь следующего события именно по
своему каналу.

## Зачем нужны `_listener_conns` и `_listener_callbacks`

Словарь `_listener_conns: dict[str, Connection]` хранит отдельное соединение для каждой очереди. Ключом служит
`queue_name`.

Он нужен, чтобы:

- не создавать новое listener connection на каждый вызов `wait_for_notification(...)`;
- переиспользовать уже зарегистрированную подписку;
- корректно закрывать listener connection в `close()`.

Словарь `_listener_callbacks: dict[str, Any]` хранит callback, переданный в `conn.add_listener(...)` для каждой очереди.

Он нужен, чтобы состояние подписки хранилось явно вместе с соединением: для каждой очереди есть соответствие между
`queue_name`, connection и callback.

---

## Как теперь устроен shutdown

При остановке worker вызывает `PGMessageQueue.close()`.

Shutdown listener-части устроен намеренно просто:

- сначала вызывается `self._event.set()`, чтобы разбудить текущее ожидание;
- затем все listener connection закрываются через `conn.close()`;
- после этого закрывается обычный PostgreSQL pool.

---

## Ограничения текущей реализации

Текущая схема решает задачу постоянной подписки, но важно учитывать ее границы:

- `asyncio.Event` сейчас общий для всех очередей внутри одного экземпляра `PGMessageQueue`;
- отдельные listener connection создаются лениво, а не на старте приложения;
- при закрытии приложения словари listener state не очищаются, потому что сам процесс завершает работу и это не влияет
  на дальнейший lifecycle.

Эти ограничения допустимы для текущего сценария, где экземпляр `PGMessageQueue` живет столько же, сколько и worker
process.
