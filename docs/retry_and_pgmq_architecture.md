## Общая схема

В проекте обработка сообщения разделена на несколько этапов:

1. Сообщение публикуется в очередь `PGMQ`.
2. Воркер читает сообщение и получает временную эксклюзивность на его обработку через visibility timeout.
3. Воркер пытается обработать сообщение.
4. По результату сообщение либо удаляется, либо откладывается для повторной попытки, либо архивируется.

Эта логика разделена между двумя зонами:

- `BaseWorker` решает, какой следующий шаг нужен после попытки обработки;
- `PGMessageQueue` выполняет физическую операцию над очередью.

---

## Жизненный цикл сообщения

Типовой сценарий выглядит так:

1. Продюсер вызывает `self._mq.send(...)`.
2. Воркер вызывает `self._mq.read(...)` и получает сообщение.
3. Во время чтения сообщение скрывается из очереди на срок `vt`.
4. Воркер выполняет `_handle_message(...)`.
5. Если обработка успешна, вызывается `self._mq.delete(...)`.
6. Если обработка требует отложенного повтора, вызывается `self._mq.set_vt(...)`.
7. Если сообщение больше не должно участвовать в нормальной доставке, вызывается `self._mq.archive(...)`.

---

## Три исхода одной попытки обработки

### `delete`

Сообщение удаляется из очереди после успешной обработки.

- сообщение доставлено успешно;
- повторять его больше не нужно;
- очередь не должна выдавать его повторно.

### `set_vt`

Используется для отложенного повтора.

- сообщение не удаляется;
- сообщение не архивируется;
- переносится момент, когда оно снова станет доступным для чтения.

### `archive`

Используется, когда сообщение больше не должно участвовать в обычной доставке.

Это конечный исход неуспешной обработки:

- ошибка признана нерелевантной для дальнейших повторов;
- исчерпан допустимый лимит повторов;
- сработала защитная ветка для неизвестных ошибок.

Архивация в этом проекте фактически играет роль DLQ.

## Уровни повторов в системе

В ChannelGateway одновременно работают несколько разных retry-механизмов.

### 1. Повторы, запланированные во время обработки

#### `ChannelToChatwootWorker`

Если Chatwoot отвечает временной ошибкой, включая HTTP 429, клиент поднимает `TransientError`, а повтор планируется
через очередь с помощью `set_vt(...)`.

#### `ChatwootToChannelWorker`

Если внешний gateway API возвращает `RateLimitError`, воркер преобразует его в `TransientError`, после чего повтор
планируется через очередь с помощью `set_vt(...)`.

### 2. Отложенные повторы через очередь

Если обработка заканчивается временной ошибкой, `BaseWorker` может не завершать жизненный цикл
сообщения, а перенести его через `set_vt(...)`.

### 3. Повторы чтения очереди

Ошибки чтения очереди обрабатываются на уровне воркера:

- исключение логируется в `_safe_read_queue(...)`;
- после возникновения исключения, воркер засыпает на `read_timeout` (10 секунд);
- затем отдает пустой список (чтобы не было исключения) и начинает следующую итерацию чтения.

### 4. Повторы после неизвестных ошибок

Если в обработке возникает исключение, которое не классифицировано для явного `set_vt(...)` или `archive(...)`,
`BaseWorker` не назначает новый visibility timeout вручную.

В этом случае сообщение:

- остается невидимым до истечения уже выданного `vt`;
- затем может быть прочитано снова;
- при `attempts > 10` архивируется защитной веткой.

Это страховочный retry-механизм на случай неразмеченных ошибок.

## Таймауты и счетчики попыток

### Базовый visibility timeout при чтении

`BaseWorker` по умолчанию читает сообщения с:

- `vt_seconds = 30` секунд;
- `message_limit = 1` сообщение за раз. Сейчас это тестовый режим, который следует изменить в дальнейшем.

### Таймауты для отложенных повторов

Если ошибка приводит к `set_vt(...)`, задержка берется из самого исключения `TransientError`, а не из отдельной
константы воркера.

В текущем коде значения по умолчанию такие:

- `retry_delay_seconds = 600` секунд (10 минут);
- `max_transient_attempts = 10`. Количество попыток. После этого сообщение будет помещено в DLQ.

### Поведение `ChannelToChatwootWorker`

Если Chatwoot возвращает временную ошибку, включая `429 Too Many Requests`, `ChatwootClient` поднимает `TransientError`.
Дальше повтор планируется через `set_vt(...)`, а задержка может браться из `Retry-After`, если этот заголовок пришел.

### Неизвестные ошибки

Если ошибка не классифицирована:

- явный `set_vt(...)` не вызывается;
- сообщение вернется в очередь после истечения текущего visibility timeout;
- при `attempts > 10` сообщение архивируется.

### Обработка `RateLimitError` в `ChatwootToChannelWorker`

- `RateLimitError` преобразуется в `TransientError`;
- задержка берется из `RateLimitError.retry_after_seconds`;
- повтор выполняется через `set_vt(...)` через `retry_after_seconds` секунд (по умолчанию, 5).

## Когда используются методы очереди

### `self._mq.send(...)`

Используется при публикации нового сообщения в очередь.

Что делает:

- сериализует полезную нагрузку;
- внедряет trace context;
- вызывает `pgmq.send(...)`.

### `self._mq.read(...)`

Используется воркером для получения сообщений из очереди.

Что делает:

- вызывает `pgmq.read(...)`;
- делает сообщение невидимым на срок `vt`;
- возвращает `msg_id`, тело сообщения и счетчик чтений `read_ct`.

### `self._mq.delete(...)`

Используется после успешной обработки сообщения.

### `self._mq.archive(...)`

Используется, когда сообщение больше не должно участвовать в обычной доставке.

С точки зрения retry-архитектуры это конечный исход всех безуспешных попыток, для которых повтор больше не нужен или
уже исчерпан.

### `self._mq.set_vt(...)`

Используется для отложенного повтора.

Это главный механизм "retry через очередь".

### `self._mq.wait_for_notification(...)`

Используется, когда новых сообщений нет.

Это не retry сообщения, а механизм экономного ожидания через PostgreSQL `LISTEN/NOTIFY`.

### `self._mq.is_already_processed(...)` и `self._mq.mark_as_processed(...)`

Эти методы относятся к инфраструктуре идемпотентности.

Они важны для общей надежности обработки, но не являются центральной частью механики повторов, описанной в этом
документе.

## Поведение воркера при простое и сбоях чтения

### Если сообщений нет

Воркер не крутится в плотном цикле. Он:

- вызывает `wait_for_notification(...)`;
- ждет уведомления о новых сообщениях от PGMQ;
- при наступлении таймаута (от 290 до 310 секунд) переподписывается на очередь и снова ждет сообщений.

### Если при чтении очереди произошла ошибка

Ошибки чтения очереди ловятся в `_safe_read_queue(...)`, логируются, после чего воркер спит `read_timeout`, который
по умолчанию равен 10 секундам.

Это отделяет ошибки инфраструктуры очереди от ошибок обработки самого сообщения и не прячет сбои внутри
дополнительного retry-слоя в `PGMessageQueue.read(...)`.

---

## Архитектурный смысл схемы повторов

Схема построена на нескольких принципах:

1. Успешное сообщение должно удаляться явно.
2. Классификация временных ошибок и отложенные повторы через очередь решают разные задачи и поэтому разделены.
3. Retry-политика должна учитывать не только бизнес-ошибки, но и сбои чтения очереди.
4. Даже для неизвестных ошибок нужен защитный предел, чтобы сообщение не крутилось бесконечно.
