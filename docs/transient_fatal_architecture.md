## Общая схема

`TransientError` и `FatalError` в проекте являются не транспортными, а архитектурными исключениями.

- `TransientError`: сбой считается временным, сообщение нужно повторить позже.
- `FatalError`: повтор без изменения данных/конфигурации бессмысленен, сообщение нужно вывести из рабочего контура.

Это разделяет две ответственности:

1. Классификация ошибки на границе интеграции.
2. Применение политики очереди в `BaseWorker`.

---

## Где объявлены классы ошибок

Классы находятся в `src/multichannel_gateway/core/exceptions.py`.

- `TransientError` хранит параметры политики повтора:
    - `retry_delay_seconds`
    - `max_transient_attempts`
- `FatalError` задает безусловную ветку «архивировать сообщение».

---

## Как BaseWorker интерпретирует ошибки

Ключевая логика находится в `src/multichannel_gateway/app/workers/base.py`, в методе `_handle_error(...)`.

- Для `TransientError`:
    - если лимит попыток не достигнут, вызывается `self._mq.set_vt(...)`;
    - если лимит достигнут, вызывается `self._mq.archive(...)`.
- Для `FatalError`:
    - сообщение сразу уходит в `self._mq.archive(...)`.
- Для прочих `Exception`:
    - используется fallback-ветка обработки.

## Где ошибки классифицируются в доменные

### 1. Chatwoot

Файл: `src/multichannel_gateway/infrastructure/chatwoot_client/cw_client.py`.

- Сетевые ошибки (`aiohttp.ClientError`, `TimeoutError`) -> `TransientError`.
- HTTP `5xx` и `429` -> `TransientError` (для `429` учитывается `Retry-After`).
- HTTP `4xx` -> `FatalError`.
- Некорректный формат ответа (`ContentTypeError`) -> `FatalError`.

При этом вызов в flow `Channel -> Chatwoot` выполняется через:
`ChatwootClient.deliver_channel_to_chatwoot_message(...)`.

### 2. Канал (на примере Telegram)

Файл: `channels/telegram_channel/tg_transport.py`.

`TelegramTransport.send_to_telegram_user(...)` не возвращает неуспешный результат, а поднимает доменные исключения
напрямую:

- временные сетевые/транспортные сбои -> `TransientError`;
- rate limit -> `RateLimitError` (дальше конвертируется в `TransientError` в worker);
- необратимые ошибки API/контракта -> `FatalError`.

`ChannelDeliveryResult` используется только для успешной доставки.

### 3. Worker Chatwoot -> Channel

Файл: `src/multichannel_gateway/app/workers/from_chatwoot.py`.

`RateLimitError` от канала переводится в `TransientError` с `retry_delay_seconds`.
Остальные необработанные ошибки идут в стандартный механизм `BaseWorker`.

## Поведение для TransientError

Текущее поведение:

- сообщение откладывается через `set_vt(...)`;
- задержка берется из `exc.retry_delay_seconds`;
- предел попыток берется из `exc.max_transient_attempts`;
- после исчерпания попыток сообщение архивируется.

Значения по умолчанию в `TransientError`:

- `retry_delay_seconds = 600`
- `max_transient_attempts = 10`

---

## Поведение для FatalError

Текущее поведение:

- `BaseWorker` сразу вызывает `archive(...)`;
- сообщение исключается из стандартного цикла доставки;
- дальнейшая обработка возможна только через ручной разбор/отдельный восстановительный процесс.

---

## Почему привязка делается на границах интеграций

Правильное место для классификации ошибки это там, где известен реальный смысл сбоя.

Например:

- только Chatwoot-клиент знает, что конкретный HTTP `500` это временная проблема внешнего сервиса;
- только адаптер знает, что `retry_after` означает допустимый повтор позже;
- только адаптер или воркер знает, что payload уже некорректен и повторять его бессмысленно.

Поэтому:

- `PGMessageQueue` не должен классифицировать такие ошибки;
- `BaseWorker` не должен знать детали конкретных API;

Это особенно важно с учетом возможного будущего выноса воркеров в отдельные контейнеры. Контракт ошибок должен остаться
одинаковым независимо от того, в каком процессе живет интеграция.

---

## Ограничения текущей реализации

- Есть fallback-ветка для `Exception`; часть ошибок может попадать туда до явной классификации.
- Качество retry-политики зависит от точности маппинга ошибок на границах интеграций.
- Для новых каналов требуется явно повторить ту же дисциплину: классификация на границе + единая обработка в
  `BaseWorker`.
