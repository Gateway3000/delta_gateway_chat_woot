## Общая схема

В проекте OpenTelemetry является базовым слоем телеметрии:

- входящие HTTP-запросы инструментируются через FastAPI;
- создаются спаны вокруг ключевых операций с очередью (`send`, `delete`, `archive`, `set_vt`);
- создаются спаны обработки сообщений в воркерах;
- trace context переносится через payload сообщений PGMQ.

Sentry не заменяет этот слой, а подключается поверх него как дополнительный потребитель OTEL-данных.

---

## Где инициализируется телеметрия

- `src/multichannel_gateway/infrastructure/telemetry/tracing.py` — настройка OTEL provider/exporter и FastAPI-инструментации.
- `src/multichannel_gateway/infrastructure/telemetry/sentry.py` — инициализация Sentry.
- `src/multichannel_gateway/app/app.py` — порядок вызовов:
  1. `setup_sentry(telemetry_settings)`
  2. `setup_tracing(app, telemetry_settings)`

Этот порядок сохранён, чтобы Sentry в режиме `instrumenter="otel"` корректно встраивался в OTEL-пайплайн.

## Условия включения OTEL и Sentry

### OpenTelemetry

Главный флаг:

```env
OTEL_ENABLED=True|False
```

Поведение такое:

- при `OTEL_ENABLED=False` функция `setup_tracing(...)` завершает работу без настройки провайдера;
- при `OTEL_ENABLED=True` создаётся/используется `TracerProvider`, настраивается sampling и FastAPI instrumentation;
- если указан `OTEL_ENDPOINT`, добавляется OTLP exporter.

### Sentry

Sentry включается только если одновременно выполнены условия:

1. `OTEL_ENABLED=True`
2. задан `SENTRY_DSN`

Если условия не выполнены, `setup_sentry(...)` ничего не делает.

## Почему Sentry опционален

Sentry вынесен в optional dependency group `sentry` в `pyproject.toml`.

Это даёт два режима установки:

- базовый (без Sentry): только OTEL/Jaeger-сценарий;
- расширенный: установка с extra `sentry` для отправки ошибок и трейсинговых данных в Sentry.

Технически это поддержано ленивым импортом `sentry_sdk` внутри `setup_sentry(...)`: при выключенном Sentry модуль не требуется на старте приложения.

---

## Почему FastAPIInstrumentor обязателен

`FastAPIInstrumentor.instrument_app(app, tracer_provider=provider)` нужен для автоматического создания серверных HTTP-спанов и корректного подхвата входящего trace context.

Без него:

- не будет автоматических спанов на запросы;
- связь между HTTP-обработчиком и внутренними спанами станет неполной;
- часть атрибутов HTTP-уровня потеряется.

---

## Context propagation через PGMQ

Реализован в `src/multichannel_gateway/infrastructure/telemetry/propagation.py`:

- `inject_trace_context(...)` — перед отправкой сообщения в очередь добавляет служебный контекст `_otel_trace_context`;
- `extract_trace_context(...)` — при чтении сообщения извлекает контекст для продолжения трассы в воркере.

Это связывает HTTP-этап и асинхронную обработку в один trace вместо разрыва на независимые trace.

## Телеметрия в тестах

В тестовой конфигурации телеметрия отключена:

```env
OTEL_ENABLED=False
```

Это убирает внешние побочные эффекты и зависимость тестов от доступности OTLP/Sentry бэкендов. Отдельно тестируется логика propagation.

## Параметры выборки для OTEL и Sentry

В проекте есть два независимых параметра выборки:

- `OTEL_SAMPLING_RATIO` для OTEL;
- `SENTRY_TRACES_SAMPLE_RATE` для Sentry.

Они отвечают за разные этапы:

- OTEL решает, какие трейсы вообще будут созданы и пройдут через основной пайплайн;
- Sentry дополнительно решает, какую долю из них он примет у себя.

Пример:

```env
OTEL_ENABLED=True
OTEL_SAMPLING_RATIO=0.5
SENTRY_TRACES_SAMPLE_RATE=0.2
```

Практический смысл:

- в OTEL-бэкенд попадёт примерно 50% трейсов;
- в Sentry попадёт примерно 20% от уже отобранных, то есть около 10% от исходного потока.

Для production-среды это позволяет отдельно регулировать объём данных в OTLP-бэкенде и в Sentry.

## Итог

Текущая архитектура телеметрии строится вокруг нескольких принципов:

1. OTEL является базовым слоем построения и переноса трейсов.
2. Sentry подключается поверх OTEL и включается отдельно.
3. Трассируются важные этапы обработки сообщения, а не каждый технический шаг.
4. Перенос контекста через `PGMQ` обязателен, иначе теряется связность трейса.
5. Единый стиль атрибутов поддерживается через вспомогательные функции.
6. В тестах реальная телеметрия отключена, но критичные механизмы, такие как перенос контекста, покрыты отдельно.
