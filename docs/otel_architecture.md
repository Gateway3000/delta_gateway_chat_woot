## Общая картина

В проекте телеметрия делится на несколько слоёв:

- HTTP-слой FastAPI, где создаются request-спаны;
- фоновые воркеры, которые читают сообщения из очереди и выполняют бизнес-обработку;
- операции над очередью `PGMQ`, такие как `send`, `read`, `delete`, `archive`, `set_vt`;
- интеграция с Sentry, которая работает совместно с OTEL, но включается отдельно.

Ключевой момент архитектуры: основная ценность этой телеметрии не в том, чтобы покрыть вообще всё, а в том, чтобы
сделать наблюдаемыми именно важные точки потока сообщения:

1. HTTP webhook получил событие.
2. Событие было опубликовано в очередь.
3. Воркер прочитал сообщение.
4. Воркер обработал сообщение.
5. Сообщение было удалено, отложено или архивировано.

## Почему выбрана связка OTEL + Sentry

Теоретически проект мог бы использовать только нативную интеграцию Sentry без отдельного OpenTelemetry слоя. Это был бы
более простой вариант на старте, но он хуже с точки зрения архитектурной гибкости.

### Почему не только Sentry

Если использовать только Sentry как единственный tracing runtime, появляются ограничения:

- приложение сильнее завязывается на одного вендора;
- локальная и production observability начинают зависеть от одного бэкенда;
- сложнее переключаться между разными системами просмотра трейсов;
- труднее строить переносимую телеметрию, которая одинаково работает в разных инфраструктурах.

### Что даёт OpenTelemetry

OpenTelemetry даёт универсальный слой instrumentation и propagation, который не зависит от конкретного бэкенда.

Это даёт несколько преимуществ:

- стандартный формат трассировки и propagation;
- возможность отправлять трейсы в разные бэкенды;
- независимость instrumentation-кода от конкретного поставщика observability;
- меньше Vendor Lock-in;
- проще локальная разработка и отладка;
- проще интеграция с инфраструктурой, где уже есть OTLP-совместимый бэкенд.

### Практический смысл

С OTEL проект может:

- локально использовать Jaeger или другой OTLP-бэкенд;
- отдельно подключать Sentry как дополнительный канал performance/error observability;
- сохранять один и тот же tracing contract внутри приложения.

Здесь OTEL является базовым транспортным слоем:

- он отвечает за создание спанов;
- он отвечает за context propagation;
- он позволяет подключать разные бэкенды;
- он делает телеметрию переносимой.

То есть instrumentation в коде остаётся стабильным, а бэкенд можно менять без переписывания всей телеметрии.

## Почему для локальной разработки предлагается использовать Jaeger

Из кода напрямую не следует, что в качестве локального бэкенда предполагается именно Jaeger. Обычно это становится
понятно по OTLP endpoint:

```env
OTEL_ENDPOINT=http://localhost:4317
```

Порт `4317` является стандартным OTLP gRPC endpoint, а в локальной разработке его удобно отдавать в контейнер Jaeger
all-in-one.

### Почему это удобно

Jaeger хорош для локальной разработки по нескольким причинам:

- он лёгкий и быстро поднимается;
- ему не нужна отдельная база данных для локального сценария;
- его можно запустить одним Docker-контейнером;
- он сразу даёт UI для просмотра трейсов;
- он избавляет от привязки локальной разработки к Sentry;
- он уменьшает Vendor Lock-in, потому что приложение отправляет телеметрию в стандартный OTLP-бэкенд, а не в
  проприетарный локальный стек.

### Когда это особенно полезно

Если у разработчика:

- нет доступа к Sentry;
- не нужен Sentry performance UI;
- нужно просто посмотреть спаны, parent-child связи и поведение воркеров;

то Jaeger является самым простым и дешёвым способом локально увидеть трассировку.

Важно: `OTEL_ENDPOINT` в проекте является опциональным.

- если `OTEL_ENDPOINT` заполнен, приложение создаёт `OTLPSpanExporter` и отправляет спаны в указанный OTLP-бэкенд;
- если `OTEL_ENDPOINT` оставлен пустым, `OTLPSpanExporter` не создаётся вообще;
- при пустом `OTEL_ENDPOINT` рантайм OTEL всё равно остаётся активным, поэтому `SentrySpanProcessor` продолжает
  работать;
- это штатный режим "только Sentry", когда не нужно отправлять телеметрию в Jaeger или другой OTLP collector.

Пример режима "только Sentry":

```env
OTEL_ENABLED=True
OTEL_ENDPOINT=
SENTRY_DSN=https://examplePublicKey@o0.ingest.sentry.io/0
```

В таком режиме приложение не пытается отправлять спаны на `http://localhost:4317` или любой другой OTLP endpoint, потому
что экспортёр OTLP просто не создаётся.

### Мини-инструкция по запуску Jaeger

#### Вариант через Docker

Нужно скачать и запустить контейнер:

```bash
docker run --rm -d \
  --name jaeger \
  -p 16686:16686 \
  -p 4317:4317 \
  jaegertracing/all-in-one:latest
```

Что означают порты:

- `4317` — OTLP gRPC endpoint, куда приложение будет отправлять спаны;
- `16686` — web UI Jaeger.

#### Как настроить приложение

Пример минимальной локальной конфигурации:

```env
OTEL_ENABLED=True
OTEL_ENDPOINT=http://localhost:4317
OTEL_INSECURE=True
OTEL_SAMPLING_RATIO=1.0
SENTRY_DSN=
```

### Что означает `OTEL_INSECURE`

- `OTEL_INSECURE=True` означает небезопасное gRPC-подключение без TLS;
- `OTEL_INSECURE=False` означает, что OTLP exporter должен использовать TLS.

Когда `OTEL_INSECURE=True` использовать нормально:

- локальный Jaeger на `localhost:4317`;
- локальный OTLP collector в Docker Compose;
- внутренний dev-стенд, где TLS сознательно не настраивался.

Когда `OTEL_INSECURE=True` использовать не нужно:

- production-среда;
- staging или shared environment, доступные по сети;
- любой внешний collector, у которого настроен TLS endpoint;
- любые случаи, где телеметрия проходит через недоверенную сеть.

Флаг `OTEL_INSECURE` имеет смысл только в комбинации с заполненным флагом `OTEL_ENDPOINT`. Если `OTEL_ENDPOINT`
пустой или отсутствует, то `OTEL_INSECURE` можно также опустить

#### Как открыть UI

После запуска контейнера нужно открыть:

```text
http://localhost:16686
```

Дальше в UI можно:

- выбрать service name;
- найти трейсы по времени;
- смотреть дерево спаны;
- анализировать связь endpoint -> queue -> worker.

### Что это даёт разработчику

Для локальной разработки Jaeger закрывает основной сценарий observability:

- видно, создаются ли спаны вообще;
- видно, работает ли propagation через очередь;
- видно, как ведут себя воркеры;
- видно, какие операции попадают в tracing, а какие сознательно не трассируются.

## Зачем нужен `log_background_task_result`

### Проблема

Воркеры запускаются как фоновые `asyncio.Task`.

Если просто сделать `asyncio.create_task(worker.run())` и не отслеживать результат, то при падении фоновой задачи можно
получить одну из двух проблем:

- исключение будет плохо видно;
- ошибка проявится слишком поздно или потеряется среди фонового шума.

Как решение, добавлен helper `log_background_task_result`, который навешивается как `done_callback` на фоновые задачи
воркеров.

### Что это даёт

- если воркер падает, это сразу попадает в лог;
- если задача отменена, это тоже фиксируется явно;
- lifecycle фоновых задач становится наблюдаемым, а не "fire-and-forget".

### Почему это важно именно здесь

В данном проекте воркеры являются критическим элементом потока сообщений. Если endpoint продолжает принимать запросы, а
воркер тихо упал, то система выглядит "живой", но фактически перестаёт доставлять сообщения дальше по pipeline. Поэтому
фоновые задачи нельзя оставлять без контроля.

## Включение глобальной телеметрии OTEL и Sentry

OpenTelemetry и Sentry включаются не по одному и тому же условию.

### OpenTelemetry

Для OTEL основным флагом является:

```env
OTEL_ENABLED=true|false
```

Если `OTEL_ENABLED=False`, телеметрия вообще не поднимается.

Дополнительно поведение OTEL exporter зависит от `OTEL_ENDPOINT`:

- если `OTEL_ENDPOINT` задан, поднимается OTLP exporter;
- если `OTEL_ENDPOINT` пустой, OTLP exporter не создаётся, но OTEL provider и Sentry processor продолжают работать.

### Sentry

Для Sentry включение требует сразу двух условий:

1. `OTEL_ENABLED=True`
2. Задание `SENTRY_DSN`

То есть Sentry не стартует:

- если телеметрия глобально выключена;
- если не задан DSN.

### Зачем это разделение

Такое разделение позволяет:

- использовать OTEL без обязательного Sentry;
- использовать Sentry поверх OTEL без обязательного OTLP collector;
- гарантированно не поднимать Sentry в тестах;
- отвязаться от Vendor Lock-in.

## Почему телеметрия не добавлена в `wait_for_notification`

Метод `wait_for_notification(...)` может срабатывать регулярно даже при отсутствии сообщений. В текущей модели ожидание
может длиться около 5 минут, после чего воркер снова уходит в цикл ожидания.

Если на каждое такое ожидание создавать спан, мы получим:

- постоянный шум от телеметрии;
- лишние спаны без бизнес-ценности;
- засорение Jaeger/Sentry однотипными событиями каждые несколько минут;
- ухудшение читаемости реальных трейсов обработки сообщений.

### Принятое решение

Телеметрия на `wait_for_notification(...)` не добавляется.

Логирование при этом сохраняется, то есть состояние ожидания остаётся наблюдаемым, но не попадает в tracing как
полноценный спан.

### Почему это правильно

Трассировать стоит то, что несёт диагностическую ценность:

- публикацию в очередь;
- чтение сообщения;
- обработку сообщения;
- ретраи;
- удаление, архивирование, перенос visibility timeout.

Ожидание новых сообщений каждые 5 минут не является такой ценной бизнес-операцией, чтобы постоянно отправлять его в
телеметрию.

## Зачем были созданы telemetry helpers

- для массовой установки span attributes;
- для единообразной установки статуса `OK` или `ERROR`;
- для сборки message-related attributes;
- для работы с propagation через очередь.

### Почему это важно

У проекта есть несколько границ:

- HTTP request;
- очередь;
- worker;
- внешние интеграции.

Если каждая граница размечается вручную по-своему, телеметрия становится несогласованной. Helpers позволяют сохранить
единый стиль по всей кодовой базе.

---

## Зачем нужен context propagation через PGMQ

### Главная проблема

HTTP endpoint и worker разорваны:

- во времени;
- по async execution context;
- потенциально по процессу.

Обычный async context не может автоматически "дотянуться" через очередь. После публикации сообщения в `PGMQ` и
последующего чтения воркером исходный request context уже не существует как "текущий".

### Что было бы без propagation

Без propagation:

- endpoint создаёт один трейс;
- worker создаёт другой трейсы;
- в Jaeger/Sentry это будут два несвязанных дерева;
- невозможно увидеть end-to-end цепочку одного сообщения.

### Что делается сейчас

Реализована parent-child модель:

1. На producer-стороне trace context инжектится в payload перед `pgmq.send(...)`.
2. В очереди payload сохраняется уже вместе со служебным OTEL metadata carrier.
3. В worker-е этот контекст извлекается обратно.
4. Consumer-спан создаётся на основе извлеченного контекста как дочерний спан от producer.

### Зачем это нужно

Это даёт полноценную distributed tracing continuity:

- видно, какой HTTP request породил сообщение;
- видно, какой worker потом это сообщение обработал;
- все дальнейшие спаны оказываются внутри одного трейса;
- проще расследовать задержки, retries и ошибки по всей цепочке.

### Важное уточнение

Передаётся не "просто `span_id`", а полноценный W3C trace context:

- `trace_id`
- `span_id`
- trace flags
- при необходимости и другой propagation metadata

Именно поэтому используется OpenTelemetry propagation API, а не ручное складывание одного поля в payload.

## Семантика `messaging.operation`

В текущей реализации `messaging.operation` используется как краткое описание действия над очередью или сообщением.

Это не просто "технический атрибут ради атрибута", а способ сделать трейсы читаемыми на уровне смысловых этапов.

### Какие значения используются сейчас

#### `send`

Используется в `pg_message_queue.py`.

Смысл:

- producer положил сообщение в очередь через `pgmq.send(...)`.

#### `receive`

Используется в `pg_message_queue.py`.

Смысл:

- backend/consumer получил сообщение из очереди.

#### `settle`

Используется в `delete`, `archive`, `set_vt` в `pg_message_queue.py`.

Смысл:

- это уже не публикация и не получение;
- это решение о дальнейшей судьбе сообщения после обработки.

#### `process`

Используется в `base.py` через `build_worker_message_attributes(...)` в `helpers.py`.

Смысл:

- consumer-воркер действительно выполняет бизнес-обработку payload.

### Зачем ещё нужен `messaging.operation.type`

Для `settle` одной верхнеуровневой категории недостаточно, поэтому добавлена детализация:

- `delete`
- `archive`
- `set_visibility_timeout`

### Почему используется именно такая схема

Потому что:

- `messaging.operation` задаёт верхнеуровневую категорию действия;
- `messaging.operation.type` задаёт подтип, когда одной категории недостаточно.

## Sampling thresholds для OTEL и Sentry

В проекте sampling настраивается отдельно для двух слоёв:

- для глобальной OTEL-трассировки через `OTEL_SAMPLING_RATIO`;
- для Sentry transaction sampling через `SENTRY_TRACES_SAMPLE_RATE`.

Это два независимых threshold-а.

### Почему они разделены

OTEL и Sentry решают разные задачи и для большей гибкости объём данных регулируется отдельно. Если Sentry выключен, то
объем телеметрии регулируется только `OTEL_SAMPLING_RATIO`

### Как считать итоговый процент телеметрии

Процент телеметрии Sentry считается от общего процента OTEL.

#### Пример 1.

```env
OTEL_ENABLED=True
OTEL_SAMPLING_RATIO=1.0
SENTRY_TRACES_SAMPLE_RATE=1.0
```

Результат:

- в OTEL-бэкенд попадёт примерно 100% трейсов;
- в Sentry попадёт примерно 100% трейсов.

#### Пример 2.

```env
OTEL_ENABLED=True
OTEL_SAMPLING_RATIO=0.5
SENTRY_TRACES_SAMPLE_RATE=0.2
```

Результат:

- в OTEL-бэкенд попадёт примерно 50% трейсов;
- в Sentry попадёт примерно 20% от 50%, т.е. около 10% всех исходных трейсов.

### Практическая рекомендация

Для прода обычно разумно:

- держать OTEL sampling выше, если важна полноценная distributed tracing картина;
- держать Sentry sampling ниже, если нужно ограничивать объём performance telemetry;
- не оставлять `1.0` везде без надобности на высокой нагрузке.

## Итог

Текущая архитектура телеметрии построена вокруг нескольких принципов:

1. В тестах телеметрия должна быть выключена явно через конфиг.
2. Фоновые воркеры нельзя оставлять без наблюдаемости.
3. Трассировать нужно не всё подряд, а только полезные операции.
4. Очередь `PGMQ` является граничным слоем, поэтому для неё нужна ручная context propagation.
5. Семантика атрибутов должна быть единообразной, поэтому используются helpers и согласованные `messaging.operation`
   значения.
