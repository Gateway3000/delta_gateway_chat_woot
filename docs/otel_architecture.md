## Общая схема

Телеметрия в проекте покрывает несколько ключевых участков:

- HTTP-слой FastAPI, где создаются спаны входящих запросов;
- публикацию сообщений в `PGMQ`;
- обработку сообщений воркерами;
- завершающие операции над сообщениями: `delete`, `archive`, `set_vt`;
- интеграцию с Sentry поверх OTEL.

Основная цель не в том, чтобы трассировать всё подряд, а в том, чтобы видеть важные этапы жизненного цикла сообщения:

1. HTTP-запрос получил событие.
2. Событие отправлено в очередь.
3. Воркер получил сообщение.
4. Воркер обработал сообщение.
5. Сообщение удалено, отложено или архивировано.

Реализация соответствует этой схеме:

- глобальная настройка OTEL находится в `src/multichannel_gateway/infrastructure/telemetry/tracing.py`;
- настройка Sentry находится в `src/multichannel_gateway/infrastructure/telemetry/sentry.py`;
- публикация и завершающие операции над сообщениями размечены в
  `src/multichannel_gateway/infrastructure/pg_message_queue.py`;
- потребление и обработка сообщений размечены в `src/multichannel_gateway/app/workers/base.py`.

## Почему выбрана связка OTEL и Sentry

Теоретически проект мог бы использовать только нативную интеграцию Sentry. Это упростило бы старт, но сделало бы
телеметрию менее гибкой.

OpenTelemetry в проекте играет роль базового слоя:

- создаёт спаны;
- передаёт контекст между частями системы;
- позволяет отправлять трейсы в OTLP-совместимый бэкенд;
- не привязывает код телеметрии к одному поставщику.

Sentry здесь играет другую роль:

- принимает ошибки;
- принимает трейсы через `SentrySpanProcessor`;
- даёт дополнительный интерфейс для анализа сбоев и производительности.

На практике это означает следующее:

- код остаётся привязан к OpenTelemetry API, а не к API конкретного сервиса;
- локально можно использовать Jaeger или другой OTLP-бэкенд;
- Sentry можно включать отдельно, если нужен его интерфейс и сбор ошибок.

Иными словами, OTEL отвечает за построение и перенос трейсов, а Sentry выступает одним из потребителей этих данных.

## Почему для локальной разработки подходит Jaeger

В коде не зашито жёсткое требование использовать именно Jaeger, но локальный сценарий на него хорошо ложится. Причина
простая: приложение умеет отправлять спаны в OTLP gRPC-узел, который обычно задаётся так:

```env
OTEL_ENDPOINT=http://localhost:4317
```

Порт `4317` является стандартным OTLP gRPC-портом. Jaeger `all-in-one` умеет принимать такие данные и подходит для
локальной отладки без дополнительной инфраструктуры.

Почему это удобно:

- Jaeger быстро запускается;
- не требует отдельной сложной конфигурации;
- сразу даёт веб-интерфейс для просмотра трейсов;
- позволяет проверить, создаются ли спаны и работает ли перенос контекста через очередь.

Пример локального запуска:

```bash
docker run --rm -d \
  --name jaeger \
  -p 16686:16686 \
  -p 4317:4317 \
  jaegertracing/all-in-one:latest
```

Пример минимальной локальной конфигурации:

```env
OTEL_ENABLED=True
OTEL_ENDPOINT=http://localhost:4317
OTEL_INSECURE=True
OTEL_SAMPLING_RATIO=1.0
SENTRY_DSN=
```

### Что означает `OTEL_INSECURE`

- `OTEL_INSECURE=True` включает gRPC-подключение без TLS;
- `OTEL_INSECURE=False` означает, что экспортёр должен использовать TLS.

Для локального `localhost` это нормально. Для общих сред и внешних коллекторов обычно нужен TLS.

### Режим "только Sentry"

Если `OTEL_ENABLED=True`, но `OTEL_ENDPOINT` пустой, OTLP-экспортёр не создаётся. При этом провайдер OTEL всё равно
поднимается, а `SentrySpanProcessor` продолжает работать.

Пример:

```env
OTEL_ENABLED=True
OTEL_ENDPOINT=
SENTRY_DSN=https://examplePublicKey@o0.ingest.sentry.io/0
```

В таком режиме приложение не отправляет спаны в OTLP-бэкенд, но может отправлять их в Sentry.

## Как включается телеметрия

### OpenTelemetry

Главный флаг:

```env
OTEL_ENABLED=true|false
```

Поведение такое:

- если `OTEL_ENABLED=False`, в `setup_tracing(...)` устанавливается `NoOpTracerProvider`;
- если `OTEL_ENABLED=True`, создаётся `TracerProvider` с `ParentBased(TraceIdRatioBased(...))`;
- если дополнительно задан `OTEL_ENDPOINT`, создаётся `OTLPSpanExporter` и `BatchSpanProcessor`;
- независимо от наличия `OTEL_ENDPOINT`, при включённом OTEL добавляется `SentrySpanProcessor`.

Кроме того, при включённом OTEL приложение инструментирует FastAPI через `FastAPIInstrumentor.instrument_app(...)`.

### Sentry

Sentry включается только при двух условиях:

1. `OTEL_ENABLED=True`
2. задан `SENTRY_DSN`

Это соответствует функции `setup_sentry(...)`: если хотя бы одно из условий не выполнено, Sentry не инициализируется.

### Порядок инициализации

В `src/multichannel_gateway/app/app.py` сначала вызывается `setup_sentry(...)`, затем `setup_tracing(...)`. Это важно,
потому что Sentry в проекте работает в режиме `instrumenter="otel"` и принимает спаны через OTEL-конвейер.

## Телеметрия в тестах

В `.test.env` задано:

```env
OTEL_ENABLED=False
```

Это отключает реальную телеметрию при запуске тестов и убирает побочные эффекты:

- не поднимаются экспортёры;
- не выполняется отправка данных во внешние системы;
- тесты не зависят от доступности Sentry или OTLP-бэкенда.

При этом в проекте есть отдельный модульный тест `tests/unit/trace_propagation_test.py`, который проверяет не отправку
телеметрии, а корректность переноса контекста трассировки через полезную нагрузку сообщения.

## Зачем нужен `log_background_task_result`

Функция `log_background_task_result(...)` используется в `src/multichannel_gateway/app/app.py` как обратный вызов для
двух верхнеуровневых задач: `incoming_worker.run()` и `outgoing_worker.run()`.

Она нужна затем, чтобы падение фонового воркера не прошло незаметно:

- при отмене задачи это явно логируется;
- при аварийном завершении исключение сразу попадает в лог;
- жизненный цикл фоновых задач перестаёт быть режимом "запустили и забыли".

Важно различать два уровня:

- `log_background_task_result(...)` следит за верхнеуровневыми задачами воркеров;
- метод `_on_task_done(...)` в `BaseWorker` следит за внутренними задачами обработки отдельных сообщений.

То есть в проекте наблюдаемость фоновых задач реализована в двух местах, но для разных уровней выполнения.

## Зачем нужны вспомогательные функции телеметрии

Во `src/multichannel_gateway/infrastructure/telemetry/helpers.py` собраны небольшие функции, которые делают разметку
единообразной:

- `set_span_attributes(...)`;
- `mark_span_ok(...)`;
- `mark_span_error(...)`;
- `build_worker_message_attributes(...)`;
- `build_webhook_attributes(...)`.

Они нужны, чтобы:

- не дублировать одну и ту же логику по всему коду;
- единообразно выставлять статус спана;
- одинаково именовать атрибуты сообщений и воркеров;
- не смешивать бизнес-логику и техническую разметку.

Это особенно важно, потому что телеметрия проходит через несколько границ: HTTP, очередь, воркер и внешние интеграции.
Без единого набора вспомогательных функций стиль быстро разъедется.

## Зачем нужен перенос контекста (context propagation) через PGMQ

### Проблема

HTTP-запрос и воркер разорваны во времени и по контексту выполнения. После публикации сообщения в очередь исходный
текущий контекст запроса больше не существует как активный.

Если ничего не делать:

- публикация сообщения попадёт в один трейс;
- обработка сообщения воркером попадёт в другой трейс;
- целостной end-to-end-картины не будет.

### Что сделано в коде

В `src/multichannel_gateway/infrastructure/telemetry/propagation.py` реализованы две функции:

- `inject_trace_context(...)`;
- `extract_trace_context(...)`.

Схема работы такая:

1. Перед `pgmq.send(...)` контекст трассировки внедряется в полезную нагрузку сообщения под ключом
   `_otel_trace_context`.
2. Сообщение сохраняется в `PGMQ` уже вместе со служебными метаданными.
3. Воркер извлекает этот контекст перед обработкой сообщения.
4. Спан `worker.queue.read` создаётся с извлечённым родительским контекстом.

Именно поэтому в интерфейсе наблюдения можно увидеть, что публикация сообщения и его обработка воркером относятся к
одному трейсу.

### Что именно переносится

Переносится не отдельный `span_id`, а полноценный W3C-контекст трассировки, который OpenTelemetry умеет внедрять и
извлекать через свой API распространения контекста. На практике это означает, что проект использует стандартный
механизм, а не собирает метаданные трассировки вручную.

### Что подтверждено тестами

В `tests/unit/trace_propagation_test.py` проверяется, что:

- в полезную нагрузку действительно добавляется `traceparent`;
- после извлечения сохраняется исходный `trace_id`;
- извлечённый родительский спан помечен как `remote`.

## Почему телеметрия не добавлена в `wait_for_notification`

Метод `wait_for_notification(...)` в `src/multichannel_gateway/infrastructure/pg_message_queue.py` предназначен для
ожидания уведомления от PostgreSQL. Он может регулярно завершаться по тайм-ауту даже тогда, когда новых сообщений нет.

Если создавать спан на каждое такое ожидание, получится:

- постоянный шум;
- большое количество однотипных спанов без диагностической ценности;
- ухудшение читаемости действительно важных трейсов.

Поэтому для `wait_for_notification(...)` оставлено только логирование, без отдельного спана.

Это соответствует общей идее проекта: трассируются полезные этапы обработки сообщения, а не каждый технический цикл
ожидания.

## Семантика `messaging.operation`

В проекте `messaging.operation` используется как краткое обозначение смыслового этапа.

Фактически сейчас используются такие значения:

### `send`

Ставится в `src/multichannel_gateway/infrastructure/pg_message_queue.py` в методе `send(...)`.

Означает, что сообщение отправлено в очередь.

### `receive`

Ставится в `src/multichannel_gateway/app/workers/base.py` для спана `worker.queue.read`.

Означает, что воркер получил сообщение и начал его потребление.

Важно: это не спан вокруг SQL-вызова `pgmq.read(...)`, а спан уровня потребителя сообщения.

### `process`

Ставится в `build_worker_message_attributes(...)` и используется для спана `worker.message.process`.

Означает фактическую бизнес-обработку сообщения.

### `settle`

Ставится в `delete(...)`, `archive(...)` и `set_vt(...)` в
`src/multichannel_gateway/infrastructure/pg_message_queue.py`.

Означает завершающее действие над уже обработанным или отложенным сообщением.

### Зачем нужен `messaging.operation.type`

Для `settle` одной общей категории недостаточно, поэтому используется дополнительный атрибут:

- `delete`;
- `archive`;
- `set_visibility_timeout`.

Такая схема делает трейсы короче и понятнее: верхний уровень показывает класс действия, а дополнительный атрибут
уточняет конкретную операцию.

## Параметры выборки для OTEL и Sentry

В проекте есть два независимых параметра выборки:

- `OTEL_SAMPLING_RATIO` для OTEL;
- `SENTRY_TRACES_SAMPLE_RATE` для Sentry.

Они отвечают за разные этапы:

- OTEL решает, какие трейсы вообще будут созданы и пройдут через основной пайплайн;
- Sentry дополнительно решает, какую долю из них он примет у себя.

Пример:

```env
OTEL_ENABLED=True
OTEL_SAMPLING_RATIO=0.5
SENTRY_TRACES_SAMPLE_RATE=0.2
```

Практический смысл:

- в OTEL-бэкенд попадёт примерно 50% трейсов;
- в Sentry попадёт примерно 20% от уже отобранных, то есть около 10% от исходного потока.

Для промышленной среды это позволяет отдельно регулировать объём данных в OTLP-бэкенде и в Sentry.

## Итог

Текущая архитектура телеметрии строится вокруг нескольких принципов:

1. OTEL является базовым слоем построения и переноса трейсов.
2. Sentry подключается поверх OTEL и включается отдельно.
3. Трассируются важные этапы обработки сообщения, а не каждый технический шаг.
4. Перенос контекста через `PGMQ` обязателен, иначе теряется связность трейса.
5. Единый стиль атрибутов поддерживается через вспомогательные функции.
6. В тестах реальная телеметрия отключена, но критичные механизмы, такие как перенос контекста, покрыты отдельно.
